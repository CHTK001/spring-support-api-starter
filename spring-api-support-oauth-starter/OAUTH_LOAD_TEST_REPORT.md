# OAuth 多协议并发承载压测报告

> 目标:验证 `spring-api-support-oauth-starter` 在真实远端环境(124.221.230.112, Ubuntu 2 核 / 1.9GB, MariaDB + Redis 本机)下,HTTP / RSocket / KCP / TCP 四种协议 + RSocket 长连接多路复用场景的并发用户承载能力。

## 环境

| 项 | 值 |
|---|---|
| 服务端 | oauth `spring-api-support-oauth-starter-4.0.0.42` |
| 部署机 | `124.221.230.112` Ubuntu 24.04, 2 核, 1.9GB;MariaDB 10.11、Redis 7.0 本机 |
| JVM | oauth `-Xmx1536m`;压测客户端 `-Xmx1g` |
| 账号 | admin / admin123,登录接口 `login` 全量走 MySQL 查询 + Redis + JWT |
| 测试客户端 | `HttpUserLoadTest` / `KcpUserLoadTest` / `RsocketUserLoadTest` / `RsocketMuxLoadTest` / `TcpUserLoadTest`(src/test/java) |

## 关键结论

1. **HTTP 承载最强**:500 并发 500/500,吞吐约 31 req/s(受认证链 DB/Redis 约束)。
2. **TCP 承载最优且稳定**:多 Reactor + 大内存后 100/200/500 全部 100% 成功。
3. **RSocket 长短连均正常**:短连 500/500;长连接多路复用 500 in-flight(10 链 × 50)500/500。
4. **KCP 并发到 500 掉包(93%)**:UDP + 丢包重传在高并发下是瓶颈,但 100/200 满载。
5. **统一瓶颈 = 认证链吞吐**:四种协议都受"同时 in-flight 认证请求数"约束,2 核 / 单机 DB+Redis 的服务端上限约 **500 并发认证**;超过后请求堆积导致客户端 30s 超时(非连接丢失,是处理过慢)。
6. **内存是硬约束**:oauth 用 `-Xmx768m` 时 500 并发认证大量 GC 停顿 → 成片超时;提到 `-Xmx1536m` 后 500/500 稳定。**该环境缺内存在 500 并压下无法避免丢请求,故最终采用 1536m。**

## 二、RSocket(19185)

### 2.1 短连接(每个用户独立连接、单请求)

| 用户数 | 成功 | 总耗时 | 平均 | P95 |
|---|---|---|---|---|
| 100 | 100/100 | 6.3s | 6.3s | 6.2s |
| 200 | 200/200 | 10.2s | 7.6s | 8.9s |
| 500 | 499/500 | 18.4s | 13.6s | 16.2s |

### 2.2 长连接多路复用(正常使用:维持长链并在同链上并发多请求) — 本次新增

| 连接数 × 每链接请求数 | in-flight | 成功 | 总耗时 | 平均 | P95 | 吞吐 |
|---|---|---|---|---|---|---|
| 20 × 50 | 1000 | 941/1000 | 31.5s | 24.1s | 30.0s | 31 r/s |
| 10 × 50 | 500 | **500/500** | 15.4s | 11.1s | 13.7s | 32 r/s |

- 同一条长连接上并发 50 个 request/response 流正常(多路复用生效)。
- 1000 in-flight 超过服务端认证吞吐 → 部分请求超过客户端 30s 窗口;500 in-flight 满载。
- 结论:RSocket 长链复用不构成瓶颈,上限仍是认证链并发(约 500)。

## 三、KCP(19186, UDP)

| 用户数 | 成功 | 平均 | P95 | 说明 |
|---|---|---|---|---|
| 100 | 100/100 | 5.6s | 4.2s | 公网 UDP |
| 200 | 200/200 | 8.4s | 17.8s | 公网 UDP |
| 500 | 465/500 (93%) | 21.5s | 27.8s | 高并发丢包 + 重传 |

- 经 `bossThreads 随核数` + `handleLine 业务异步派发虚拟线程` 优化,500 并发从 354/500提升至 465/500。
- 残余瓶颈:UDP 高并发下的丢包与 KCP 重传竞争,以及认证链吞吐。

## 四、TCP(19187, TcpSyncServer)

| 用户数 | 成功 | 平均 | P95 | 说明 |
|---|---|---|---|---|
| 100 | 100/100 | 4.8s | 6.5s | 回环 |
| 200 | 200/200 | 6.2s | 8.3s | 回环 |
| 500 | **500/500** | 19.8s | 23.8s | 回环,1536m |
| 100 | 100/100 | 3.1s | 4.4s | 公网 |

- `TcpSyncServer` 升级为主从多线程 Reactor 后,纯网络层 500 并发回环 echo 500/500(单线程版本 273/500)。
- 认证场景下 500/500 稳定,是四种协议中并发承载最稳的。

## 五、实现中交付的协议/性能修复

| 项 | 内容 |
|---|---|
| KCP | `ServerSetting.bossThreads` 默认 = CPU 核数;`KcpServer.handleLine` 业务异步派发虚拟线程 |
| TCP | `TcpSyncServer` 主从多线程 Reactor(boss accept + N worker selector)、IO 缓冲线程本地复用、`drainLines` 字节级切行、非阻塞写续写 |
| RSocket | `requestResponse/fireAndForget` 业务异步派发虚拟线程,避免阻塞连接 event loop |
| OAuth server | 恢复多协议 Server 启动(`startAll`),新增 SyncServer 通用适配(支持 TCP/WebSocket/UDP) |
| 压测工具 | 全部支持远程 host 参数;新增 `RsocketMuxLoadTest`(长链复用)、`TcpUserLoadTest` |

## 六、后续优化建议(未实施)

- **认证链背压/排队**:认证入口加 `Semaphore` 限流(按核数×K),宁可排队拉长延迟、保证 0 失败(慢不丢)。
- **DB 连接池/索引**:确认登录 3-4 条 SQL 的连接池水位与 `sys_user.username` 索引。
- **水平扩展**:单机认证吞吐上限约 500 in-flight,更大并发需横向扩容或引入认证缓存。
