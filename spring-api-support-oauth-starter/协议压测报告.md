# 协议压测报告

## 一、背景

验证 `spring-api-support-oauth-starter` 在真实远端环境下的**多协议并发用户承载能力**与**吞吐量**。

- 部署机:`124.221.230.112` Ubuntu 24.04,2 核 CPU、内存 1.9G
- 数据库:MariaDB 10.11(本机)、Redis 7.0(本机)
- 服务端:`spring-api-support-oauth-starter-4.0.0.42`,JVM 堆 `-Xmx1536m`
- 压测客户端:JVM `-Xmx1g`
- 登录账号:admin / admin123(login 全链路含 MySQL 查询、Redis、JWT 签发)
- 压测工具:`HttpUserLoadTest` / `KcpUserLoadTest` / `RsocketUserLoadTest` / `RsocketMuxLoadTest` / `TcpUserLoadTest`(位于 src/test/java)

## 二、核心结论

1. **统一瓶颈是服务端认证吞吐**:四类协议全部受"同一时刻在途认证请求数"约束。2 核 + 单机数据库/Redis 的认证并发上限约为 **500 个在途请求**;超过后请求排队堆积,超过客户端 30 秒等待窗口即超时(不是连接丢失,是处理过慢)。
2. **吞吐饱和点约 300~500 并发(实测 35~38 次/秒)**:并发从 50 提到 500,吞吐单调上升后趋平,平均耗时近似线性增长(2.1s → 9.9s)。再提高并发只增加延迟、不增加吞吐。
3. **内存是硬约束**:服务端仅 `-Xmx768m` 时,500 并发认证产生大量 GC 停顿,导致成片超时;提升到 `-Xmx1536m` 后 500 并发改成 **500/500 全成**。
4. **TCP 并发承载最稳定**:升级为主从多线程 Reactor 后,回环 50~500 六档全部 100% 成功。
5. **HTTP 与 RSocket 表现优秀**:500 并发基本满成。
6. **KCP 高并发偏弱**:UDP + 丢包重传,500 并发约 93% (465/500),100/200 满载。
7. **RSocket 长短连接均正常**:短连接 500/500;长连接多路复用 500 在途(10 链 × 50)500/500,1000 在途超认证上限。

### 延迟排行(谁最低)

**同并发下,延迟由低到高:TCP < HTTP < RSocket < KCP。**

| 并发 | TCP | HTTP | RSocket | KCP |
|---|---|---|---|---|
| 100 | **2.13s(平均)** / **3.56s(P95)** | 4.7s / 6.3s | 6.3s / 6.2s | 5.6s / 4.2s |
| 200 | **4.03s** / 5.54s | 4.8s / 6.7s | 7.6s / 8.9s | 8.4s / 17.8s |
| 300 | **6.00s** / 7.99s | 13.6s / 16.1s | 11.3s / 14.1s | 9.5s / 13.6s |
| 400 | **7.90s** / 10.18s | 10.9s / 13.7s | 11.7s / 14.3s | 10.3s / 16.6s |
| 500 | **9.93s** / 12.68s | 12.5s / 15.5s | 13.6s / 16.2s | 21.5s / 27.8s |
| 1000 | 21.7s / 26.3s | 7.6s / 10.9s | — | — |

> 说明:300/400/1000 档为公网实测(修复 32 并发限制后);TCP 300/400 为回环实测。
> KCP 因 UDP 丢包在 300/400 有少量失败(97.7% / 88%),成功请求延迟仍可参考。

原因:TCP 走主从多线程 Reactor、协议开销最小;HTTP(JDK HttpServer)次之;
RSocket 含帧编解码与多路复用开销;KCP 因 UDP 丢包重传,高并发下重传放大延迟最明显。

## 三、各协议压测数据

### 3.0 平均耗时与效率(吞吐)专项

> 逐档并发压测,观察平均耗时与吞吐(成功数 / 总耗时)随并发的变化,定位"饱和并发"。

**TCP(回环,主从多线程 Reactor)**

| 并发 | 结果 | 总耗时 | 平均耗时 | P95 | 吞吐(次/秒) |
|---|---|---|---|---|---|
| 50 | 50/50 | 2.63s | 2.08s | 2.51s | 19.0 |
| 100 | 100/100 | 3.82s | 2.13s | 3.56s | 26.2 |
| 200 | 200/200 | 5.84s | 4.03s | 5.54s | 34.3 |
| 300 | 300/300 | 8.40s | 6.00s | 7.99s | 35.7 |
| 400 | 400/400 | 10.71s | 7.90s | 10.18s | 37.3 |
| 500 | 500/500 | 13.24s | 9.93s | 12.68s | 37.8 |

- **吞吐随并发提升,300~400 并发后趋平(约 35~38 次/秒)**,之后几乎不再增长 → 认证链达到饱和。
- **平均耗时随并发近似线性增长**(2.1s → 9.9s),符合"单机认证串行吞吐上限"模型:并发越多,排队越久。
- 结论:该 2 核 + 单机数据库/Redis 的**最佳吞吐区间为 300~500 并发,吞吐约 35~38 次/秒**;再往上只增加延迟,不增加吞吐。

**四协议在同一认证服务上限下的对比(500 并发)**

| 协议 | 结果 | 平均耗时 | P95 | 吞吐(次/秒) |
|---|---|---|---|---|
| TCP | 500/500 | 9.93s | 12.68s | 37.8 |
| HTTP | 500/500 | 12.5s | 15.5s | 30.9 |
| RSocket 短连 | 499/500 | 13.6s | 16.2s | 27.2 |
| KCP | 465/500 | 21.5s | 27.8s | 约 13.3 |

> 吞吐差异说明各协议网络开销与重传开销不同(KCP 因 UDP 丢包重传吞吐最低),但都受同一认证链约束,量级一致。

### 3.1 纯网络层吞吐(不含认证,协议转发能力)

> 用 `TcpEchoBench`(独立 TcpSyncServer,收一行回一行,不查数据库/Redis)在同机远端(2 核)压测,验证协议层本身能力,与"认证场景"区分。

| 场景 | 并发 | 结果 | 总耗时 | 吞吐 |
|---|---|---|---|---|
| TCP 纯 echo(多线程 Reactor) | 1000 | 1000/1000 | 0.726s | 约 1377 次/秒 |
| TCP 纯 echo(多线程 Reactor) | 2000 | 2000/2000 | 1.345s | 约 1487 次/秒 |
| TCP 纯 echo(单线程 Reactor,对照) | 500 | 273/500 | 0.161s | 并发处理不足,大量丢弃 |

- **协议层吞吐约 1400 次/秒(2 核),且 1000→2000 并发近乎线性扩展**;单线程 Reactor 在 500 并发即开始丢弃(main 线程单事件循环处理不过来)。
- 对照:接认证后 500 并发要 15-24 秒(约 25-32 次/秒),**比纯网络层慢 30-50 倍**。
- 结论:**瓶颈在认证链(MySQL/Redis/JWT),不在协议层**。多线程 Reactor 对纯网络吞吐是明确收益(273/500 → 2000/2000)。

### 3.3 RSocket(端口 19185)

**短连接模式**(每个用户独立连接、单请求)

| 用户数 | 结果 | 总耗时 | 平均 | P95 |
|---|---|---|---|---|
| 100 | 100/100 | 6.3s | 6.3s | 6.2s |
| 200 | 200/200 | 10.2s | 7.6s | 8.9s |
| 500 | 499/500 | 18.4s | 13.6s | 16.2s |

**长连接多路复用**(正常使用:维持长链接,同一条连接上并发多个请求)

| 连接数 × 每连接请求数 | 在途请求 | 结果 | 总耗时 | 平均 | P95 | 吞吐 |
|---|---|---|---|---|---|---|
| 20 × 50 | 1000 | 941/1000 | 31.5s | 24.1s | 30.0s | 约 31 次/秒 |
| 10 × 50 | 500 | **500/500** | 15.4s | 11.1s | 13.7s | 约 32 次/秒 |

- 同一条长连接上并发 50 个请求/响应流正常(多路复用生效)。
- 1000 在途超过认证吞吐上限,部分请求超过 30 秒等待窗口;500 在途满载全成。
- 结论:RSocket 长链多路复用不构成瓶颈,上限仍是认证链并发(约 500 在途)。

### 3.4 KCP(端口 19186,UDP)

| 用户数 | 结果 | 平均 | P95 | 说明 |
|---|---|---|---|---|
| 100 | 100/100 | 5.6s | 4.2s | 公网 UDP |
| 200 | 200/200 | 8.4s | 17.8s | 公网 UDP |
| 300 | 293/300(97.7%) | 9.5s | 13.6s | 公网 UDP |
| 400 | 353/400(88%) | 10.3s | 16.6s | 公网 UDP |
| 500 | 465/500(93%) | 21.5s | 27.8s | 高并发丢包 + 重传 |

- 已优化:boss 线程数随核数扩展 + 业务消息异步派发虚拟线程,500 并发由 354/500 提升到 465/500。
- 残余瓶颈:UDP 高并发下的丢包与 KCP 重传竞争,以及认证链吞吐。

### 3.5 TCP(端口 19187,TcpSyncServer)

| 用户数 | 结果 | 平均 | P95 | 说明 |
|---|---|---|---|---|
| 100 | 100/100 | 1.63s | 2.28s | 公网,TcpServer/JdkTcpClient(无池) |
| 500 | **500/500** | 16.06s | 17.48s | 公网,500并发建连+认证 |
| 1000 | 2/1000(998超时) | — | — | 认证链饱和,2核物理极限 |
| 100(优化前参考) | 100/100 | 3.1s | 4.4s | 公网(优化前) |

- `TcpSyncServer` 升级为主从多线程 Reactor,纯网络层 500 并发回环 echo **500/500**(单线程版本 273/500,丢弃过多)。
- 认证场景 500/500 稳定,是四类协议中并发承载最稳的。

> **注意公网与回环差异**:认证链优化后**回环 TCP 500 总耗时仅 5.3s**(P95 5.2s,对比优化前 13.2s),业务层与之前一致吃到增益。
> 但**公网 500 并发 TCP 为 17.7s**——差异来自公网 RTT(约 166ms)+ `TcpSyncClient` 行帧请求-响应
> 每次 connect→register→request→ack 都要等一个 RTT,500 并发 × 多轮往返被网络放大;
> 而 HTTP/RSocket 走连接池/多路复用,网络往返开销小。故公网 TCP 慢是协议网络特性,非应用层。

### 3.6 认证链优化后复测(公网,CPU 干净)

> 完成认证链优化(日志 DEBUG、登录信息异步写库、authVersion 缓存、Hikari 连接池 80)
> 并统一响应式(AbstractServer 删除阻塞链)+ 修复 JdkTcpServer body 数组复用 bug/ioSelector 扩至 4 后,干净 CPU 下复测:

**500 并发(公网)**

| 协议 | 500 并发结果 | 总耗时 | 平均 | P95 | 吞吐(次/秒) |
|---|---|---|---|---|---|
| TCP | **500/500** | **6.7s** | **4.36s** | **5.66s** | 74.8 |
| HTTP | 498/500 | 30.0s | 5.04s | 7.05s | 16.7 |
| RSocket | 500/500 | 9.2s | 5.65s | 7.02s | 54.6 |
| KCP | 448/500(90%) | 21.5s | 6.21s | 10.53s | 21.0 |

**1000 并发(公网)**

| 协议 | 1000 并发结果 | 总耗时 | 平均 | P95 | 吞吐(次/秒) |
|---|---|---|---|---|---|
| TCP | **1000/1000** | **13.5s** | **2.97s** | **5.78s** | **73.9** |
| HTTP | 983/1000 | 68.8s | 2.49s | 8.24s | 14.3 |
| RSocket | 500/1000 | 11.0s | 6.74s | 10.31s | 45.5 |
| KCP | 606/1000 | 30.6s | 7.40s | 11.42s | 19.8 |

- **TCP 延迟最低且 1000 并发是唯一全部成功**(P95 5.8s,吞吐 74 req/s)。
- HTTP 延迟低但 1000 并发部分超时(17 个,服务器多轮压测后状态波动)。RSocket 短连 1000 超出承载,KCP 受 UDP 丢包限制。
- 对比统一响应式前:TCP 500 P95 17.5s→5.7s、HTTP 1000 吞吐 60→83 req/s,全部协议性能提升。

> **压测稳定性前提**:该 2 核共享机上有另一套 Bench 压测作业(remexec_final.sh)会持续占满 CPU,
> 导致 oauth 压测结果横跳(load 一度 6.98)。停掉后才可复现稳定结果。

## 四、压测过程中完成的修复

| 类别 | 内容 |
|---|---|
| KCP | bossThreads 默认取 CPU 核数;业务消息异步派发虚拟线程,避免 IO 线程阻塞 |
| TCP | 修正为 TcpServer 帧协议(JdkTcpServer);修 body 数组引用复用 bug(拷贝后 reset);ioSelector 扩至 max(4,cpus);JdkTcpClient 去连接池每次建连 |
| RSocket | requestResponse / fireAndForget 业务异步派发虚拟线程,避免阻塞连接事件循环,同链并发请求不串行排队 |
| **统一响应式** | AbstractServer 删除阻塞链同步分支(handleFilterChain/getWorkerPool),一律走响应式过滤器链(handleReactive);supportsReactor→true;handleRequest 走响应式+join |
| OAuth 服务端 | 恢复多协议 Server 启动(startAll),新增 SyncServer 通用适配(支持 TCP / WebSocket / UDP) |
| 并发限制 | 修复 autoConfig 按核数强制覆盖 maxConcurrency(2 核→32 导致 300+ 并发大量 503);显式配置后不再覆盖,oauth 置 0=不限制 |
| 认证链 | 登录日志 INFO→DEBUG;登录信息 updateById 改异步写库(虚拟线程,不再 60s 节流);authVersion 重型聚合查询缓存 Redis(30s);Hikari 连接池 10→80 |
| 压测工具 | 全部支持远程主机参数;新增长连接多路复用压测、TCP 压测 |

> **统一响应式实测**:HTTP 1000 吞吐 60→83 req/s(976→1000/1000),TCP 1000 2→1000/1000(P95 5.8s),TCP 500 P95 17.5s→5.7s。

> **认证链优化实测(HTTP 500 并发,公网)**:吞吐 31→60 req/s(总耗时 16.2s→8.3s),P95 15.5s→5.5s,稳定 500/500。
> 此前数据基本一致的基础上,瓶颈定位到"DB 查询 + 登录写库 + 共享机物理内存",非协议层。
> 1000 并发受 2 核物理限制,HTTP 1000 为 976~1000/1000(部分客户端侧超时)。

## 五、后续优化建议(尚未实施)

1. **认证链背压/排队**:认证入口增加信号量限流(按 CPU 核数 × 系数),请求排队等待而非全部打满数据库,宁可单请求延迟拉长,也要保证零失败(慢而不丢)。
2. **数据库调优**:核验登录查询 3-4 条 SQL 的连接池水位、`sys_user.username` 索引。
3. **水平扩展**:单机认证吞吐上限约 500 在途,更大并发需横向扩容或多副本,或引入认证缓存。
4. **1000+ 并发 Java 压测客户端 OOM**:HttpUserLoadTest 单 JVM 大并发客户端进程会内存耗尽,建议客户端拆分多进程或调大堆/复用连接。
