# 支付中心化接入说明

## 一、目标

在保留 `spring-support-payment-starter` 可嵌入能力的前提下，支持两种部署模式并存：

- 嵌入式模式：业务模块自己承载支付接口、回调、调度、运营台
- 中心化模式：业务模块继续依赖 `spring-support-payment-starter`，但关闭调度与运营台；由 `spring-api-support-payment-starter` 统一承载支付运维能力

## 二、能力边界

### 2.1 保留在 `spring-support-payment-starter` 的核心能力

- 商户、渠道、订单、退款、钱包、微信支付分核心接口
- 发起支付
- 手工同步订单状态
- 支付/退款/钱包/支付分回调处理
- 钱包账务闭环
- 回调地址解析与生成

### 2.2 可由中心化服务统一承载的能力

- 支付调度任务
- 任务配置与执行管理
- 支付运营台接口
- 回调异常重试与清理的统一运维入口

## 三、当前开关

`spring-support-payment-starter` 已支持以下开关：

```yaml
plugin:
  payment:
    scheduler:
      enabled: true
    ops:
      enabled: true
```

说明：

- `plugin.payment.scheduler.enabled`
  - 控制调度线程池、调度管理器、托管任务是否启用
- `plugin.payment.ops.enabled`
  - 控制 `/api/ops/**` 运营台接口是否启用
  - 该能力依赖调度管理器，通常与 `scheduler.enabled` 配套使用

## 四、嵌入式模式

适用场景：

- 单体应用
- 单个业务服务自己管理支付
- 不需要独立支付中心

建议配置：

```yaml
plugin:
  payment:
    scheduler:
      enabled: true
    ops:
      enabled: true
    callback:
      base-url: https://biz.example.com
```

特点：

- 当前服务自己生成默认回调地址
- 当前服务自己执行超时关单、回调重试、回调清理等任务
- 当前服务直接暴露运营中心接口

## 五、中心化模式

适用场景：

- 多个业务模块共用一套支付基础设施
- 希望统一支付运维、统一调度、统一查看回调异常
- 避免多服务同时执行同一批支付调度任务

### 5.1 中心化支付服务

使用模块：

- `spring-api-support-payment-starter`

建议配置：

```yaml
plugin:
  payment:
    scheduler:
      enabled: true
    ops:
      enabled: true
    callback:
      base-url: https://pay.example.com/payment/api
```

职责：

- 统一执行支付调度任务
- 统一暴露运营中心接口
- 统一作为默认支付回调接收服务

### 5.2 其它业务模块

这些模块仍然可以直接依赖 `spring-support-payment-starter`，但建议关闭调度与运营台：

```yaml
plugin:
  payment:
    scheduler:
      enabled: false
    ops:
      enabled: false
    callback:
      base-url: https://pay.example.com/payment/api
```

职责：

- 继续调用 starter 的核心支付能力
- 创建订单、发起支付、处理业务侧调用
- 不再重复执行支付调度任务
- 不再暴露本地运营台接口
- 默认回调地址统一指向支付中心

## 六、中心化模式的关键前提

### 6.1 数据库必须共享

如果中心化支付服务要执行：

- 超时关单
- 回调异常重试
- 回调异常清理
- 运营台查询

那么它必须连接和业务模块相同的支付数据库，看到同一批：

- 支付订单
- 退款单
- 回调日志
- 钱包订单
- 调度任务配置

否则中心化服务拿不到业务模块创建的数据，调度就没有意义。

### 6.2 默认回调地址必须统一

`spring-support-payment-starter` 的默认回调地址来自：

- `plugin.payment.callback.base-url`

如果业务模块仍在本地生成默认回调 URL，而该值配置成业务服务自己的地址，那么第三方回调仍会打回业务服务，而不是支付中心。

所以中心化模式下，业务模块应把：

```yaml
plugin:
  payment:
    callback:
      base-url: https://pay.example.com/payment/api
```

统一指向支付中心。

### 6.3 显式覆盖仍然优先

当前回调 URL 解析优先级仍是：

1. 请求显式传入的 notifyUrl
2. 渠道配置 notifyUrl
3. 商户 defaultNotifyUrl
4. `plugin.payment.callback.base-url` 生成的默认 scoped 路由

所以如果你希望严格收口到支付中心，要避免业务侧继续写死其它回调地址。

## 七、推荐落地方式

### 方案 A：完全中心化

- 所有业务模块保留 `spring-support-payment-starter`
- 所有业务模块关闭 `scheduler/ops`
- 所有业务模块统一把 `plugin.payment.callback.base-url` 指向支付中心
- `spring-api-support-payment-starter` 独立部署并开启 `scheduler/ops`

适合：

- 多业务线共享支付
- 统一值班、统一回调诊断

### 方案 B：局部嵌入式

- 某些业务模块自己承载支付
- 某些业务模块接入支付中心

适合：

- 渐进迁移
- 存量系统与新系统并存

前提是按系统边界清楚区分数据库、回调入口和运维职责。

## 八、不建议的模式

不要让多个服务同时满足以下条件：

- 指向同一套支付库
- `plugin.payment.scheduler.enabled=true`

否则会出现多实例同时扫单、重试、清理的问题，虽然部分逻辑幂等，但运维层面会混乱。

## 九、当前默认建议

- `spring-api-support-payment-starter`
  - `plugin.payment.scheduler.enabled=true`
  - `plugin.payment.ops.enabled=true`
- 其它业务模块
  - `plugin.payment.scheduler.enabled=false`
  - `plugin.payment.ops.enabled=false`

这样可以同时满足：

- starter 仍能独立赋能
- 中心化服务统一承担支付运维职责
- 不强制所有模块都必须依赖支付中心才能工作
